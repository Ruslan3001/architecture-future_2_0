# Task 4. Обоснование Terraform-конфигурации

## 1. Выбор ресурсов и параметров

Конфигурация воспроизводит текущий ландшафт «Будущее 2.0» из схемы потоков данных: каждый компонент схемы получает собственную виртуальную машину, диск и сетевой интерфейс.

### 1.1. Виртуальные машины

| ВМ (роль) | Cores | Memory | Диск | NAT | Обоснование |
|-----------|-------|--------|------|-----|-------------|
| `dwh` | 4 | 8 GB | 100 GB SSD | нет | DWH — центральное хранилище; больше CPU/RAM и диска для СУБД и исторических данных. |
| `bi` | 2 | 4 GB | 30 GB SSD | нет | BI-сервер средней нагрузки. |
| `operator` | 2 | 4 GB | 20 GB SSD | да | Клиент оператора; NAT нужен для доступа к обновлениям и внешним сервисам. |
| `esb` | 2 | 4 GB | 30 GB SSD | да | ESB Apache Camel — точка интеграции, NAT для внешних взаимодействий. |
| `internal` | 2 | 4 GB | 30 GB SSD | нет | Внутренние сервисы компании. |
| `ai` | 2 | 8 GB | 50 GB SSD | нет | ML/ИИ-сервисы требуют больше RAM для моделей и датасетов. |
| `fintech` | 2 | 4 GB | 30 GB SSD | нет | Финтех-сервисы на Go/Java. |

### 1.2. Диски

- Тип `network-ssd` — стандартный сетевой SSD Yandex Cloud, достаточный для учебного стенда: баланс цены и производительности.
- Размеры выбраны по ролям: DWH получает 100 GB, остальные — 20–50 GB, так как на них разворачиваются легковесные приложения на Ubuntu.

### 1.3. Сеть

- **VPC Network + Subnet `10.0.0.0/24`** — изолированная сеть для всех сервисов; 256 адресов достаточно для стенда.
- **NAT Gateway + Route Table** — позволяет ВМ выходить в интернет (обновления, пакеты), но не открывает весь кластер извне.
- **Security Group** — разрешает SSH (22) извне, весь трафик внутри подсети и любой outbound. Это базовый минимум для управляемости и безопасности стенда.

## 2. Декларативный подход

Terraform описывает желаемое состояние инфраструктуры, а не последовательность команд. Это даёт:

- **Единый источник истины** — `main.tf`, `variables.tf`, `outputs.tf` и `terraform.tfvars` содержат всё состояние.
- **Предсказуемость** — `terraform plan` показывает, что именно изменится, прежде чем применить.
- **Версионирование** — конфигурация хранится в Git; изменения отслеживаются код-ревью.
- **Откат** — при необходимости можно вернуть предыдущую версию инфраструктуры через Git + `terraform apply`.

## 3. Infrastructure as Code (IaC)

IaC повышает воспроизводимость и масштабируемость:

- **Воспроизводимость**: один и тот же `terraform apply` разворачивает идентичный стенд в любой папке или даже в другом облачном каталоге.
- **Масштабируемость**: чтобы добавить ещё одну ВМ, достаточно добавить одну запись в `terraform.tfvars` в блок `vms`; Terraform сам создаст диск и инстанс.
- **Автоматизация**: инициализация, планирование и применение выполняются командами, что позволяет встроить развёртывание в CI/CD.
- **Снижение ошибок**: ручная настройка сети, дисков и ВМ исключается; человеческий фактор остаётся только в настройке ПО, которое нельзя автоматизировать одним Terraform (лицензии, данные, роли).

## 4. Что управляется Terraform, а что — вручную

**Terraform управляет:**
- VPC Network, Subnet, NAT Gateway, Route Table, Security Group.
- Compute Disks и Virtual Machines (включая SSH-ключи в metadata).

**Настраивается вручную / через Ansible:**
- Установка и конфигурация ПО: MS SQL Server 2008, PowerBuilder, Power BI, Apache Camel, Python/ML, Go/Java.
- Загрузка данных, миграции, бэкапы, DNS-записи, агенты мониторинга.
- Настройка IAM-ролей и политик доступа на уровне приложений.

Такое разделение соответствует принципу **железо и сеть — в коде, приложения и данные — через configuration management**.
